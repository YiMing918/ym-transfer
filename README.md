## 功能一览

| 功能 | 说明 |
|---|---|
| 免注册上传 | 打开网页就能传，不收账号、不收邮箱 |
| 大文件直传 | 单文件最大 5 GB，浏览器直传 R2，不经过服务器中转 |
| 有效期可选 | 1 / 6 / 12 小时、1 / 3 / 7 天，到期自动删除 |
| 下载次数可选 | 不限 / 1 次 / 5 次 / 10 次，用完链接立即失效（原子计数，并发打开也不会超发）。计数口径：计的是「经下载页领取直链的次数」，每次领到的直链 1 小时内有效；链接预览/扫描不会耗次数 |
| 随机链接 | 链接 ID 为 128 位随机值，猜不到；拿到链接的人都能下载 |
| 自动清理 | 定时清理（每 6 小时）+ 访问过期链接时顺手删 + R2 生命周期 10 天兜底，三层保险 |
| 防刷限流 | 同一 IP 每小时最多创建 10 次上传（IP 只存哈希，不存明文） |
| 容量保护 | 全站 10 GB 上限（免费 R2 额度），满了会明确提示等旧文件过期 |
| 站点统计 | 首页可见已用空间与文件数（公开接口 `/api/stats`） |

部署这个项目，你要先准备好下面几样东西。每样都写了「是什么、去哪弄、免费多少」，全部准备完再进下一节。

| # | 要准备的东西 | 是什么（人话） | 去哪弄 | 免费吗 |
|---|---|---|---|---|
| 1 | Cloudflare 账号 | 本项目跑的平台：网站托管、文件存储、数据库都在它家。后面说的「CF 控制台」就是它的管理后台 | 打开 https://dash.cloudflare.com 点「Sign up（注册）」，用邮箱注册并按邮件验证 | 免费注册；本项目用到的 Pages / R2 / D1 都有免费额度，本项目全程 0 元 |
| 2 | GitHub 账号 | 放代码的网站；方式一靠它自动部署，清理任务也靠它的定时器（Actions，就是 GitHub 提供的自动跑脚本服务） | 打开 https://github.com 点「Sign up」注册 | 免费；公开仓库的 Actions 免费 |
| 3 | 本仓库的代码 | 就是这个项目本身 | 方式一/三：点仓库页右上角「Fork」复制一份到你自己账号下，或用 git 克隆；方式二：下 Releases 里的部署包 zip | 免费（MIT 许可） |
| 4 | 一台能上网的设备 | 电脑最好（方式一、三）；只有手机也能干（方式二） | —— | —— |
| 5 | Node.js（只有方式三需要） | 在电脑上跑命令的运行环境，wrangler 命令行工具靠它 | https://nodejs.org 下 LTS 版一路下一步安装 | 免费 |
| 6 | 一个自己的域名（**可选**） | 不绑域名也能用，站点地址是 `你的项目名.pages.dev`；想用 `file.你的域名.com` 这种地址才需要 | 在任何域名商处注册均可；绑到 Cloudflare 的方法见「可选：绑你自己的域名」 | 域名本身要花钱（几十元/年），不绑就不花 |

几个后面反复出现的词，先在这里说清：

- **Pages**：Cloudflare 的网站托管服务，这个项目的网页和接口代码就住在这里。
- **R2**：Cloudflare 的文件仓库（对象存储），访客传的文件本体存在这里。
- **D1**：Cloudflare 的数据库（SQL 数据库），存每个分享链接的记录（文件名、大小、过期时间、还能下几次）。
- **绑定（Binding）**：在 Pages 设置里把 D1、R2「挂」给网站用，并给它们起个代号（本项目代号固定是 `DB` 和 `FILES`，代码按代号找它们，代号写错网站就找不到库和桶）。
- **变量 / 密钥（Secret）**：网站运行时要用的配置和钥匙。普通配置叫「变量」，怕泄露的钥匙叫「密钥（加密变量）」——存进去之后页面上只显示名字、看不到值。
- **预签名地址**：服务端用 R2 钥匙临时签出来的一次性链接，浏览器拿着它直接跟 R2 传/下文件，所以大文件不用经过网站服务器。

### 先分清两个地方：GitHub 和 Cloudflare 各管什么

部署时你会在两个网站之间来回跑，先分清它们谁管什么，后面每一步说「去 GitHub 做 X」「去 Cloudflare 做 Y」你就不会迷路。

**GitHub = 放代码的地方**（像一个代码仓库 + 工具间）：

| GitHub 里的东西 | 在哪 | 干什么用（本项目里） |
|---|---|---|
| 仓库（Repository） | github.com 上你的项目页 | 存放本项目的全部代码；方式一的自动部署就是从这里取代码 |
| Actions（自动干活的机器人） | 仓库页顶部的「Actions」标签页 | 代码推送后自动帮你部署（`deploy`）、每 6 小时自动调一次清理接口（`cleanup`）、每次推送先跑一遍测试（`ci`）——都是 GitHub 免费提供的自动任务，不用你守着 |
| Releases（发行页） | 仓库页右侧的「Releases」 | 放打包好的部署包 zip 给人下载；方式二下的就是这里的包 |
| Secrets（钥匙保险柜） | 仓库页「Settings（设置）」→ 左侧「Secrets and variables」→「Actions」 | 存钥匙的地方：Actions 机器人干活时要用的令牌、密码都放这里，存进去之后谁也看不到值，只能覆盖重填 |

**Cloudflare = 让项目跑起来的地方**（代码部署到这里才变成能打开的网站），控制台是 https://dash.cloudflare.com ：

| Cloudflare 里的东西 | 在控制台哪个菜单 | 干什么用（本项目里） |
|---|---|---|
| Pages | 左侧「Workers 和 Pages（Workers & Pages）」 | 网站本体住这里：网页、接口代码都在 Pages 项目里运行，你的站点地址也是它给的 |
| D1 | 左侧「D1 SQL 数据库」 | 存分享链接的记录（文件名、大小、过期时间、还能下几次），是表格形式的数据库 |
| R2 | 左侧「R2 对象存储」 | 存访客上传的文件本体；桶的「设置（Settings）」里有 **CORS 策略**设置（管「允许哪个网站的浏览器直接往桶里传文件」，不配好上传会失败，见共同准备第 2 步） |

**两边怎么配合，一句话**：代码在 GitHub →（部署）→ 跑在 Cloudflare 的 Pages 上；访客传的文件实物存在 R2 里、每条分享记录在 D1 里——**文件和记录都不在 GitHub 上**，所以重新部署代码不会丢已传的文件，以后迁移也要记得桶和库是分开搬的。

做到这里你应该：Cloudflare 和 GitHub 两个账号都已注册并能登录，代码已 Fork 到你的 GitHub 账号下（或部署包 zip 已下载好）。

## 部署总览：三种方式对比

| 对比项 | 方式一：连 GitHub 自动部署 | 方式二：手机部署包上传 | 方式三：wrangler 命令行 |
|---|---|---|---|
| 需要的设备 | 电脑或手机浏览器都行 | **只要手机** | 必须有电脑 |
| 上手难度 | 中（要配仓库密钥） | 低（下载、上传、点几下） | 高（要装环境、敲命令） |
| 第一次大约耗时 | 40–60 分钟（含共同准备） | 30–45 分钟（含共同准备） | 45–75 分钟（含装环境和共同准备） |
| 日常更新方便度 | **最方便**：改完代码推送一次就自动上线 | 最麻烦：每次更新都要重新下包、重新上传 | 一般：敲一条命令部署一次 |
| 出错了好不好排查 | 好：GitHub 的 Actions 页有每一步日志 | 差：控制台提示少，出错只能靠现象猜 | 好：命令输出直接写明错在哪 |
| 适合谁 | 想长期用、以后还会改代码的人（**推荐大多数人选它**） | 没电脑救急、把站点迁移到另一个 CF 账号 | 熟悉命令行、想完全本地掌控的人 |

**三种方式的共同点**：下面「部署前的共同准备」（建 R2 桶、建 D1 库、领 R2 钥匙）哪种方式都要先做一遍，跳不过去。区别只在「代码怎么送上 Pages」这一步。

## 部署前的共同准备（三种方式都要先做）

不管你选哪种部署方式，下面 4 件事都要先在 Cloudflare 控制台做一遍（做一次，以后更新代码不用重做）。每件都写了在哪点、填什么。

### 第 1 件：建 R2 存储桶（放文件本体的仓库）

1. 打开 https://dash.cloudflare.com ，登录后在左侧菜单点「R2 对象存储（R2 Object Storage）」。（第一次用 R2 时它可能让你先点一下开通免费计划，照着点，不会扣费。）
2. 点「创建存储桶（Create bucket）」。
3. 名称填 `ym-transfer-files`（必须一字不差，后面好几处要对上这个名字），位置选「自动（Automatic）」，点「创建（Create）」。
4. **不要**给桶开公开访问、**不要**绑 r2.dev 公开域名——下载是靠预签名地址的，桶保持私有反而更安全。

做到这里你应该看到：R2 的桶列表里多了一个 `ym-transfer-files`，点进去是空的。

### 第 2 件：给桶配 CORS（不配，浏览器传不上文件）

CORS（一句话：浏览器的一道安检规则，规定「哪个网站的页面可以直接往这个桶里传/取文件」，名单里没有你的站点，浏览器就把请求拦下来，上传会报错）。

1. 在 R2 里点进 `ym-transfer-files` 桶 → 点上方「设置（Settings）」标签 → 找到「CORS 策略（CORS Policy）」→ 点「添加（Add）/ 编辑（Edit）」。
2. 打开仓库里的 `r2-cors.json` 文件，把内容粘进去，但**先改一行**：文件里 `AllowedOrigins` 写的是示例地址 `https://ym-transfer.pages.dev`，把它改成**你自己的站点地址**（还没部署、还不知道地址？先原样粘上，部署完拿到 `你的项目名.pages.dev` 地址后，回来把这一行改成你的地址，再把你以后绑的自定义域名也加进来——一行一个，逗号隔开）。
3. 保存。

做到这里你应该看到：CORS 策略框里有一段 JSON，`AllowedMethods` 里有 `PUT`、`GET`、`HEAD`，`AllowedOrigins` 里是你（将要）的站点地址。

> 用命令行的同学（方式三）：`npx wrangler r2 bucket cors put ym-transfer-files --file r2-cors.json` 一条命令等效，同样记得先改文件里的域名。

### 第 3 件：建 D1 数据库并建表（存分享记录的表格）

1. 控制台左侧点「D1 SQL 数据库（D1 SQL Database）」→ 点「创建数据库（Create database）」。
2. 名称填 `ym-transfer-db`，点创建。
3. 建表：在 D1 列表里点进 `ym-transfer-db` → 点「控制台（Console）」标签 → 把仓库里 `schema/0001_init.sql` 文件的**全文**粘进输入框 → 点「执行（Execute）」；再把 `schema/0002_add_max_downloads.sql` 全文粘进去执行一次；最后 `schema/0003_drop_redundant_index.sql` 也执行一次（可选，不跑不影响使用）。
   - 三个文件**顺序不能错**，先 0001 再 0002。0002 是「下载次数上限」那一列，不跑它，访客选了下载次数的上传会直接报错。
   - 表结构都写了防重复，同一个文件重复执行也不会坏，放心。
4. 顺手记下这个库的「数据库 ID（一串字符）」：点进库就能在页面上看到。方式三要用；方式一、二不用手填（在后台绑定时是点选的）。

做到这里你应该看到：执行时提示成功（Success），在「数据表」里能看到 `files` 等表名。

> 用命令行的同学：`npx wrangler d1 execute ym-transfer-db --remote --file=schema/0001_init.sql`，换文件名再跑两次，等效。

### 第 4 件：领 R2 的 S3 钥匙（网站签发上传/下载地址用的）

这把钥匙是给网站程序用的：访客点上传时，网站用它给 R2 签一张一次性的「预签名地址」，浏览器才能直传。它是本项目最重要的一把钥匙，按五点说清：

- **①是什么**：一对值——`Access Key ID`（钥匙编号）+ `Secret Access Key`（钥匙本体），合起来相当于 R2 桶的专用账号密码，但权限只限指定的一个桶。
- **②去哪领（点位步骤）**：控制台 →「R2 对象存储」→ 点页面上的「API 令牌（API Tokens）」→「创建 API 令牌（Create API Token）」→ 权限选「对象读写（Object Read & Write）」→ 指定存储桶只勾 `ym-transfer-files` → 创建。
- **③领完先抄下来**：创建成功页会显示 Access Key ID、Secret Access Key，还有你的**账号 ID**（在控制台首页右侧也能看到）。S3 端点（网站连 R2 用的地址）就是 `https://<你的账号ID>.r2.cloudflarestorage.com`，把账号 ID 换进去即可，不用另找。
- **④干什么用**：填进 Pages 的密钥里（后面部署方式里会让你填），网站靠它签发预签名上传/下载地址。没有它，点上传会报 `sign_failed`。
- **⑤保存与丢失**：⚠️ **Secret Access Key 只完整显示这一次**，关掉页面就再也看不到——**当场复制，存进你的密码管理器或记事本**（连同 Access Key ID、账号 ID 一起存）。真丢了也不用慌：回「API 令牌」页把旧令牌删掉、重新建一对，把新值填回 Pages（和 GitHub Secrets，如果用了方式一 B 路线）即可，桶里的文件不受影响。

做到这里你应该：手里有一份记好的三件套（Access Key ID、Secret Access Key、账号 ID），桶和库都建好了。

### 第 5 件（可选但建议）：给桶加生命周期兜底

桶 →「设置」→「生命周期规则（Lifecycle rules）」→ 添加一条：**对象创建 10 天后删除**。作用：万一自动清理哪天漏删了，文件最晚 10 天也会被 R2 自己删掉。本站文件最长有效期是 7 天，10 天这条线不会误删还在有效期内的文件。

## 方式一：连 GitHub 自动部署（推荐）

**优势**

- 以后改代码只要推送（push，就是把新代码上传到 GitHub 仓库）一次，站点自动更新，不用再碰 Cloudflare 后台。
- 每次推送仓库自带的测试（ci）会先跑一遍，坏代码会先在 Actions 页亮红灯提醒你。
- 部署记录、回滚都在 Pages 后台有据可查，出问题能退回上一个版本。

**劣势**

- 第一次配置最繁琐：要么在 Pages 后台手填绑定和密钥，要么在 GitHub 里配一堆 Secrets，新手容易漏填一样。
- 本仓库有**两条自动部署路线，只能选一条**（下面 A、B 二选一），两条都开会互相覆盖、排障时互相误导——这是新手最容易踩的坑，下面写清了怎么选。

### 要用到的东西

- 共同准备的全部成果：R2 桶 `ym-transfer-files`（含 CORS）、D1 库 `ym-transfer-db`（已建表）、R2 的 S3 钥匙三件套。
- 你 Fork 到自己账号下的 GitHub 仓库。
- 下面 A、B 两条路线**二选一**要配的东西：
  - **A 路线（Pages 连 Git 直连）**：不用配任何 GitHub Secrets；绑定和密钥直接在 Pages 后台填。
  - **B 路线（Actions 直推，本站现行方式）**：要在 GitHub 仓库里配 6 个 Secrets（下面第 3 步逐个列），换来的是密钥自动同步、连建表都自动跑。

### 步骤

**第 1 步：在 Cloudflare 建 Pages 项目并连上仓库**

1. 控制台 →「Workers 和 Pages」→「创建（Create）」→ 选「Pages」标签 →「连接到 Git（Connect to Git）」。
2. 按提示授权 Cloudflare 访问你的 GitHub，选中你 Fork 的 `ym-transfer` 仓库，生产分支选 `main`。
3. 构建设置这样填：**框架预设（Framework preset）选 `None`**、**构建命令（Build command）留空**、**构建输出目录（Build output directory）填 `public`**。
   - 为什么输出目录是 `public`：网页文件都在仓库的 `public/` 文件夹里；接口代码在仓库根目录的 `functions/` 文件夹，Pages 连 Git 时会自动认根目录的 `functions/`，不用你管。
4. 点「保存并部署（Save and Deploy）」。

做到这里你应该看到：Pages 开始第一次部署。**这次大概率失败或部署完打开站点接口报错，别慌**——绑定和密钥还没配，下一步配好再部署一次就好。

**第 2 步：配绑定和普通变量（A、B 两条路线都要做）**

1. 进你的 Pages 项目 →「设置（Settings）」→「绑定（Bindings）」→「添加（Add）」：
   - 选「D1 数据库」：变量名填 `DB`，数据库选 `ym-transfer-db`，保存。
   - 再「添加」一次：选「R2 存储桶」：变量名填 `FILES`，桶选 `ym-transfer-files`，保存。
   - ⚠️ 变量名 `DB`、`FILES` 必须一字不差——代码是按这个代号找库和桶的，写错等于没绑。
2. 同页的「变量和密钥（Variables and Secrets）」里添加两个**普通变量**（类型选「文本（Text）」）：
   - `R2_S3_ENDPOINT` = `https://<你的账号ID>.r2.cloudflarestorage.com`（把 `<你的账号ID>` 换成共同准备第 4 件里记下的账号 ID）；
   - `R2_S3_BUCKET` = `ym-transfer-files`。

做到这里你应该看到：绑定列表里有 DB、FILES 两行，变量列表里有 R2_S3_ENDPOINT、R2_S3_BUCKET 两行。

<details>
<summary><b>第 3 步：配密钥（点开看，A / B 两条路线分开写，二选一）</b></summary>

**A 路线（Pages 后台手填）**：在刚才的「变量和密钥」里，类型选「密钥（Secret）」，逐个添加下面 4 个，值就是共同准备和这里说明的：

| 变量名 | 值填什么 |
|---|---|
| `R2_ACCESS_KEY_ID` | 共同准备第 4 件记下的 Access Key ID |
| `R2_SECRET_ACCESS_KEY` | 共同准备第 4 件记下的 Secret Access Key |
| `TASK_SECRET` | **自己编**一个随机串当口令（见下方说明），例如用密码生成器生成 32 位以上随机字符 |
| `IP_SALT` | （可选，建议配）同样自己编一个随机串，只填这里、不用和别处一致 |

- `TASK_SECRET` 是什么：清理接口的口令。自动清理任务每次来删过期文件时要报这个口令，对不上就不许删。它不是谁发给你的，**是你自己编、自己记好**的。以后方式一的清理工作流里还要填同一个值（见「自动更新 / 自动任务」），两边必须一模一样。
- 配完后到「部署（Deployments）」页 → 最新一条部署右边「···」→「重新部署（Retry deployment）」，让新配置生效。

**B 路线（GitHub Secrets + Actions 直推）**：

1. 先断开第 1 步的 Git 直连（避免两条路打架）：Pages 项目 →「设置」→「构建和部署（Build & deployments）」→ 断开 Git 集成。项目保留，不用删。
2. 打开你的 GitHub 仓库页 →「Settings（设置）」→ 左侧「Secrets and variables」→「Actions」→「New repository secret（新建）」，逐个添加下面 6 个：

| Secret 名 | 值填什么 | 干什么用（细节见「凭据一览」） |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | Cloudflare 的 API 令牌（见下方「这把令牌去哪建」） | 部署机器人操作你 CF 账号的钥匙 |
| `CLOUDFLARE_ACCOUNT_ID` | 你的账号 ID | 告诉机器人部署到哪个账号 |
| `R2_ACCESS_KEY_ID` | 共同准备第 4 件的 Access Key ID | 机器人转手灌进 Pages 当运行时密钥 |
| `R2_SECRET_ACCESS_KEY` | 共同准备第 4 件的 Secret Access Key | 同上 |
| `TASK_SECRET` | 自己编的随机串（和将来 Pages 里的必须一样，机器人会灌过去，两边天然一致） | 清理接口口令 |
| `SITE_URL` | `https://你的项目名.pages.dev`（部署完拿到地址后填/改） | 清理工作流要调的站点地址 |

   - **这把 `CLOUDFLARE_API_TOKEN` 去哪建**：Cloudflare 控制台右上角头像 →「我的个人资料（My Profile）」→「API 令牌（API Tokens）」→「创建令牌（Create Token）」→ 选「编辑 Cloudflare Workers（Edit Cloudflare Workers）」模板（它包含 Pages 编辑、D1 编辑等本项目需要的权限）→ 创建。⚠️ **令牌值只完整显示一次，当场复制**，直接粘进 GitHub Secrets；没来得及复制就关了页面，只能删掉重建（见「凭据一览」）。
3. 添加完后，随便推送一次代码（或到仓库「Actions」页 → 选 `deploy` 工作流 →「Run workflow（运行）」手动跑一次）。它会自动：跑一遍建表 SQL → 把上面 3 个运行时密钥灌进 Pages → 拼好目录并部署。
   - ⚠️ **第一次跑**时 Pages 项目若还不存在，「灌密钥」那一步会先失败但不中断，部署会把项目建出来；然后你**再手动跑一次 `deploy`**，密钥灌入后随第二次部署生效。看到第一次有一步黄/红提示先别慌，按这个说明再跑一次即可。

**第 4 步：回来补 CORS 名单**

部署成功后你的站点地址就定下来了（`你的项目名.pages.dev`，在 Pages 项目页顶部能看到）。回共同准备第 2 件，把这个真实地址填进 R2 桶 CORS 的 `AllowedOrigins`（替换掉示例地址），保存。不补这一步，网页能打开但一上传就报 CORS 错。

### 部署完怎么验

按「部署完怎么验（自测清单）」逐项过，重点第 1、2 项先过：首页能打开、传一个小文件能拿到链接并下载成功，就算主体通了。

### 常见问题

- **部署时提示找不到 `functions` 或接口全 404**：A 路线检查构建输出目录是不是 `public`、仓库根目录有没有 `functions/` 文件夹；千万别把 `wrangler.toml.example` 改名成 `wrangler.toml` 提交——一旦项目里出现带绑定段的 `wrangler.toml`，Pages 后台的绑定/变量会被锁定改由文件管理，新手会直接卡死。本项目的做法就是**不用**这份文件，后台配即可。
- **两条路线都配了、行为怪怪的**：就是 A、B 打架了。定一条：想用 B 就按上面断开 Git 集成；想用 A 就不要配 `CLOUDFLARE_API_TOKEN` 那两个 Secrets（`deploy` 工作流没令牌会自动跳过，不会报错），并可删掉仓库里的 `.github/workflows/deploy.yml`。
- **站点能开、上传报 `sign_failed`**：运行时密钥没配或配错——检查 Pages 里 `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` 两个密钥在不在、值对不对，`R2_S3_ENDPOINT` 里账号 ID 有没有写错。改完密钥记得重新部署一次才生效。
- **改了绑定/变量没反应**：Pages 的绑定和变量是「下一次部署生效」，改完必须重新部署（部署页「···」→「重新部署」）。

## 方式二：手机部署包（不用电脑）

**优势**

- 全程只要一部手机：下载、解压、上传、点设置，全在浏览器里完成。
- 包是拼好结构的成品，不用懂仓库目录怎么回事。
- 适合救急，或者把站点整体迁移到另一个 Cloudflare 账号。

**劣势**

- 以后每次更新代码，都要重新下新包、重新上传一遍，没有自动部署。
- 绑定、密钥还是得在 Pages 后台一格一格填，省不掉（但只需第一次，重新传包不会清掉它们）。

### 要用到的东西

- 共同准备的全部成果（桶、库、钥匙——换新 CF 账号迁移时，这些要在新账号里重新建一遍）。
- Releases 页下载的两个文件：`ym-transfer-deploy-日期.zip`（部署包）和 `ym-transfer-SHA256SUMS.txt`（校验文件）。
- 手机浏览器（要能打开 Cloudflare 控制台的完整版页面；控制台提示用 App 或桌面版时选继续用浏览器）。

### 步骤

**第 1 步：下载并解压部署包**

1. 打开 https://github.com/YiMing918/ym-transfer/releases/latest ，在「Assets（附件）」里点 `ym-transfer-deploy-日期.zip` 下载，再点 `ym-transfer-SHA256SUMS.txt` 下载。
2. 用手机文件管理器解压 zip。解压后**根目录**应该直接是：`index.html` 文件 + `functions/` 文件夹（里面是 api、d 等子文件夹）。
   - ⚠️ **层级千万别错**：要传的是「`index.html` 和 `functions/` 这一层」，不是把 `public/` 文件夹、更不是把整个 zip 或多套一层文件夹传上去。多套一层，Pages 就找不到首页，打开是 404。

**第 2 步（可选但建议）：核对校验文件**

`SHA256SUMS.txt` 里写着部署包的 SHA-256 指纹。手机上用任何能算文件 SHA-256 的工具（文件管理器或哈希计算 App）算一下你下的 zip，指纹和文件里写的一致，说明包完整、没下坏。用电脑的同学：`sha256sum ym-transfer-deploy-日期.zip`（Mac 是 `shasum -a 256`）。

**第 3 步：在 Cloudflare 建 Pages 项目并上传**

1. 手机浏览器打开 https://dash.cloudflare.com →「Workers 和 Pages」→「创建」→「Pages」→ 选「上传资产（Upload assets）」。
2. 项目名填 `ym-transfer`（或你喜欢的名字，它决定 `项目名.pages.dev` 这个地址），点创建。
3. 把第 1 步解压出的**那一层全部内容**上传（`index.html` + `functions/` 文件夹，按控制台提示拖放或逐个选文件；文件夹要整体传，不能只传里面的文件丢掉文件夹结构）。
4. 点「部署（Deploy）」。

做到这里你应该看到：部署完成，给你一个 `项目名.pages.dev` 地址，打开能看到中文首页（先别试上传，绑定还没配）。

**第 4 步：配绑定、变量、密钥**

和方式一的第 2 步、第 3 步 A 路线**完全一样**：

1. 项目 →「设置」→「绑定」：加 D1 绑定 `DB` → `ym-transfer-db`；加 R2 绑定 `FILES` → `ym-transfer-files`。
2. 「变量和密钥」：加普通变量 `R2_S3_ENDPOINT`、`R2_S3_BUCKET`；加密钥 `R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`、`TASK_SECRET`（自己编的随机串，记好，以后配清理任务还要用同一个）、`IP_SALT`（可选）。
3. 回「部署」页对最新部署点「···」→「重新部署」，让配置生效。

**第 5 步：回来补 CORS 名单**

把你的 `项目名.pages.dev` 真实地址填进 R2 桶 CORS 的 `AllowedOrigins`（共同准备第 2 件），保存。

### 部署完怎么验

同「部署完怎么验（自测清单）」。另外注意：方式二**没有** GitHub Actions 的自动清理任务，过期文件只靠「有人打开过期链接时顺手删」和桶的 10 天生命周期兜底。想要定时清理，照「自动更新 / 自动任务」里说的，把仓库的 `cleanup` 工作流接到你的仓库上（需要先 Fork 仓库）。

### 常见问题

- **打开站点是 404 / 空白**：99% 是上传层级错了（多套了一层文件夹）。重新上传，记住传的是「解压后第一层的内容」。
- **首页能开、上传失败**：先查 CORS 名单里有没有你的真实地址，再查第 4 步的密钥有没有漏填 `R2_SECRET_ACCESS_KEY`。
- **重新上传新包后要不要重配绑定**：不用。绑定、变量、密钥存在项目设置里，重新部署代码不会清掉它们；只有换新 CF 账号才要重配。

## 方式三：wrangler 命令行部署

wrangler（一句话：Cloudflare 官方的命令行工具，在电脑终端里敲命令就能建库、传代码、改密钥，不用点网页）。

**优势**

- 所有步骤都是命令，可复制、可重复；出错时终端直接打印原因，排查最快。
- 建桶、建表、部署、灌密钥一条线走完，不用来回切网页。

**劣势**

- 要先装 Node.js 和 wrangler，纯新手光装环境就可能卡住。
- 本项目部署前要**手动拼一次目录**（下面第 3 步），拼错就丢接口，是这条路线特有的坑。

### 要用到的东西

- 电脑 + Node.js（官网 LTS 版）+ 终端（Windows 用 PowerShell，Mac 用「终端」）。
- 本仓库代码（git 克隆或下 Source code 解压；也可以用 Releases 的部署包代替第 3 步的拼目录）。
- 共同准备可以在命令行里顺手做，下面步骤里给了等效命令。

### 步骤

**第 1 步：装 wrangler 并登录**

```bash
npm install -g wrangler
wrangler login
```

`wrangler login` 会弹浏览器让你授权，点允许。做到这里你应该看到：终端提示登录成功（Successfully logged in）。

**第 2 步：建桶、建库、建表（网页版见共同准备，命令版如下）**

```bash
wrangler r2 bucket create ym-transfer-files
wrangler d1 create ym-transfer-db
wrangler d1 execute ym-transfer-db --remote --file=schema/0001_init.sql
wrangler d1 execute ym-transfer-db --remote --file=schema/0002_add_max_downloads.sql
wrangler d1 execute ym-transfer-db --remote --file=schema/0003_drop_redundant_index.sql
wrangler r2 bucket cors put ym-transfer-files --file r2-cors.json
```

注意：`r2-cors.json` 里的示例域名要先改成你部署后将用的地址（项目名定了就是 `https://ym-transfer.pages.dev`，项目名自定义就换成你的）；R2 的 S3 钥匙（Access Key ID / Secret Access Key）命令行领不了，仍要按共同准备第 4 件在网页控制台领，当场记好。

**第 3 步：拼部署目录（关键，别省）**

```bash
rm -rf _site && mkdir _site
cp -r public/. _site/
cp -r functions _site/functions
```

为什么要拼：Pages 只认「部署目录里面的 `functions/`」。网页在 `public/`、接口在仓库根的 `functions/`，直接部署 `public` 会把接口丢掉（`/api/*` 全部 404）。拼完 `_site/` 里应该是：`index.html` + `functions/` 文件夹。用部署包 zip 的同学跳过本步——包里已经是拼好的，解压目录就是 `_site` 本体。

**第 4 步：先在后台绑一次绑定（只此一次）**

命令行部署**没法凭空创建后台绑定**：先去 Pages 后台（项目此时可能还不存在——先执行第 5 步部署一次把项目建出来，再回来）→「设置」→「绑定」加上 `DB` → `ym-transfer-db`、`FILES` → `ym-transfer-files`；「变量和密钥」加上普通变量 `R2_S3_ENDPOINT`、`R2_S3_BUCKET`（值同方式一第 2 步）。

**第 5 步：部署并灌密钥**

```bash
wrangler pages deploy _site --project-name ym-transfer --branch main
printf '%s' '你的Access Key ID' | wrangler pages secret put R2_ACCESS_KEY_ID --project-name ym-transfer
printf '%s' '你的Secret Access Key' | wrangler pages secret put R2_SECRET_ACCESS_KEY --project-name ym-transfer
printf '%s' '你自己编的随机串' | wrangler pages secret put TASK_SECRET --project-name ym-transfer
printf '%s' '你自己编的另一个随机串' | wrangler pages secret put IP_SALT --project-name ym-transfer
wrangler pages deploy _site --project-name ym-transfer --branch main
```

最后再部署一次，是让刚灌的密钥生效。做到这里你应该看到：终端打印出部署成功的地址，打开是中文首页。

### 部署完怎么验

同「部署完怎么验（自测清单）」。

### 常见问题

- **`/api/*` 全是 404**：第 3 步没拼目录或拼错了，检查 `_site/functions/` 在不在。
- **`wrangler login` 卡住或失败**：换网络重试；或改用 API 令牌方式（环境变量 `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID`），令牌建法见「凭据一览」。
- **上传报 `sign_failed`**：密钥没灌对，重新跑第 5 步的 secret put 两条 R2 命令，再部署一次。

## 部署完怎么验（自测清单）

部署完别急着发给别人用，先自己在你的站点地址（`https://你的项目名.pages.dev` 或你的自定义域名）上逐项过一遍，全过才算部署成功：

1. 打开首页：是中文界面，「站内已用」显示 `0 / 10 GB`。
2. 传一个小文件（如 1 MB 的图片）：进度条走完 → 出现下载链接 → 复制 → 用浏览器的**无痕窗口**打开链接，能下载，文件名和原文件一样（中文名正常）。
3. 传一个较大文件（如 200 MB 的视频）：上传正常，下载后比对大小一致。
4. 打开一个不存在的链接（如在地址后拼 `/d/00000000000000000000000000000000`），应看到中文「不存在」页。
5. （可选，进阶）超限拦截：`curl -X POST https://你的地址/api/upload-init -H 'Content-Type: application/json' -d '{"name":"x","mime":"application/octet-stream","size":5368709121,"expires_hours":72}'` 应返回 400 `bad_size`——不用真传 5 GB 文件，接口先校验就够了。
6. （可选）去 R2 桶里看一眼：第 2 步传的文件对象在桶里；去 D1 的 `files` 表看一眼：有对应一行、状态是 `ready`。
7. （可选）过期验证：D1 里把一个文件的 `expires_at` 改成过去的时间，再打开它的下载链接，应提示已过期，且 R2 对象和 D1 记录都被顺手删掉。

哪一项不过，先去对应部署方式的「常见问题」对症，再去「常见问题」总章找。

## 凭据一览：每样钥匙是什么、存哪、丢了怎么办

本项目一共涉及下面这些「钥匙」。通用规矩先说清：**任何钥匙都不许写进仓库里的任何文件**（代码是公开的，写进去等于公开）；能选「密钥（Secret，加密变量）」类型时一定选它。

| 名称 | ①是什么 | ②去哪建/拿 | ③填到哪用 | ④干什么用 | ⑤保存与丢失 |
|---|---|---|---|---|---|
| `R2_ACCESS_KEY_ID` + `R2_SECRET_ACCESS_KEY` | R2 桶的 S3 钥匙一对（编号 + 本体） | CF 控制台 → R2 →「API 令牌」→ 创建，权限选对象读写、只限 `ym-transfer-files` 桶（点位步骤见共同准备第 4 件） | Pages「变量和密钥」里的两个同名**密钥**；方式一 B 路线还要在 GitHub Secrets 里放同名两份（机器人会灌进 Pages） | 网站用它签发预签名上传/下载地址；没有它上传报 `sign_failed` | ⚠️ **Secret Access Key 只完整显示一次，当场复制存进密码管理器**。丢了：删旧令牌、新建一对，所有填过的地方换成新值 |
| 账号 ID（Account ID） | 你 CF 账号的编号，不是秘密 | CF 控制台首页右侧就有；拼 `R2_S3_ENDPOINT` 和填 GitHub Secret `CLOUDFLARE_ACCOUNT_ID` 时用 | 见左 | 定位「是哪个账号」 | 不用特意保存，丢了回控制台首页看 |
| `TASK_SECRET` | 清理接口的口令，一串你自己编的随机字符 | 不是领的，是**自己生成**的：密码生成器或 `openssl rand -hex 32` | Pages 的同名**密钥** + GitHub Secrets 的同名一份（cleanup 工作流用），**两边必须一模一样** | cleanup 任务调 `/api/cleanup` 时报口令，对不上不许删 | 自己记好（和站点配置一起存密码管理器）。丢了/忘了：随便换一个新的，两边一起换，再部署一次 |
| `IP_SALT` | 给访客 IP 哈希时加的「盐」（一串随机字符，让哈希猜不回原 IP） | 自己生成，方法同上 | 只填 Pages 的同名**密钥**（可选，但强烈建议） | 限流计数时给 IP 哈希加盐 | 不配时代码用一个公开默认值兜底，功能正常但盐等于公开。丢了换新即可，换盐后旧的限流计数作废重来，无其他影响 |
| `CLOUDFLARE_API_TOKEN` | 部署机器人的 CF 钥匙（仅方式一 B 路线 / 方式三令牌登录时用） | CF 控制台右上角头像 →「我的个人资料」→「API 令牌」→「创建令牌」，选「编辑 Cloudflare Workers」模板 | GitHub Secrets 同名一份（B 路线）；方式三则放电脑环境变量 | Actions 机器人拿它替你部署、建表、灌密钥 | ⚠️ **只完整显示一次，当场复制**。平时不用看（GitHub Secrets 存着）；丢了：CF 里删掉旧令牌、新建一把，GitHub Secrets 里换成新值 |

做到这里你应该：密码管理器里至少存好 R2 钥匙一对和 `TASK_SECRET` 这两样，别的丢了都有路可退，这两样丢了要多绕几步。

## 出事了怎么办（丢了 / 坏了 / 删了：后果 + 能不能重建 + 怎么重建）

先记住数据都在哪：**文件实物在 R2 桶、分享记录在 D1、钥匙在 Pages 的「变量和密钥」里、代码在 GitHub。** 哪样出事，先在表里对号入座——大多数都能重建，只有标了 ❌ 的两样，东西没了是真的没了。

| 清理任务停了 | 过期文件不再自动删，R2 用量只涨不降 | ✅ 查原因 + 手动跑一轮 |

**R2 桶被删**
- 出事情形：在 CF 控制台 R2 页手滑把 `ym-transfer-files` 桶删了（删桶要再输一遍桶名确认，但真能发生）。
- 后果：桶里所有文件实物**永久消失，Cloudflare 没有回收站**。D1 里的分享记录还在，但下载时找不到对象，会失败。
- 能不能重建：桶能重建（空的），文件不能。
- 重建步骤：① CF 控制台 → 左侧「R2 对象存储」→「创建存储桶」，名字还填 `ym-transfer-files`；② 进新桶 →「设置」→ CORS 策略，把仓库里 `r2-cors.json` 的内容（域名改成你自己的）整段贴回（就是共同准备第 2 件）；③ 生命周期兜底规则按共同准备第 5 件重新加一遍；④ Pages 项目 →「设置」→「绑定」，确认 R2 绑定 `FILES` 指着这个桶（同名重建一般自动对上，对不上就重新选一次），然后重新部署一次。
- 影响范围：旧分享链接**全部作废**（记录还在、文件没了）；新上传恢复正常。重要文件别只存一份在这里——本站本来就是临时中转。

**D1 被删**
- 出事情形：控制台里把 `ym-transfer-db` 库删了。
- 后果：分享记录（哪个链接、有效期、还剩几次）全没；R2 里就算还有文件实物，也成了没记录的孤儿——下载入口是先查记录的，查不到就打不开，等于全站文件一起失效。
- 能不能重建：库能重建（空的），记录不可恢复。**预防就一条**：时不时去 CF 控制台 →「D1」→ 你的库 →「导出」下个备份文件存好；真删了又恰好有备份，下面的第 ④ 步能把记录导回来。
- 重建步骤：① 「D1」→「创建数据库」，名字还填 `ym-transfer-db`；② 进库 →「控制台（Console）」，把 `schema/` 里 0001、0002、0003 三个文件的内容按顺序粘贴执行（同共同准备第 3 件）；③ Pages →「设置」→「绑定」，D1 绑定 `DB` 重新选这个新库，重新部署一次；④ 有备份的：在电脑上跑 `npx wrangler d1 execute ym-transfer-db --remote --file=备份文件.sql` 把记录导回。
- 影响范围：没备份时旧分享链接全部作废；R2 里的孤儿文件还白占着用量，去桶里手动清空即可。

**R2 S3 钥匙被删 / 怀疑泄露**
- 出事情形：钥匙令牌被删、或怀疑被人看过。
- 后果：网站签不出上传/下载地址——上传报 `sign_failed`、下载页签不出直链，全站传不了也下不了。但文件和记录都还在，没丢。
- 重建步骤：① CF 控制台 → R2 →「API 令牌」，**先删旧令牌**（泄露时这步最要紧，先删先止损），再「创建 API 令牌」：权限选对象读写、只限 `ym-transfer-files` 桶，当场把新的一对复制好（Secret Access Key 只显示一次）；② Pages 项目 →「设置」→「变量和密钥」，把 `R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY` 换成新值；③ 用了方式一 B 路线的，GitHub Secrets 里同名两份也一起换；④ 重新部署一次生效，回站点传一个小文件验一下。
- 影响范围：换钥匙之前已签发出去的临时地址（上传地址最长 6 小时、下载直链最长 1 小时）**立即作废**——正传一半的上传要重新开始；但**分享链接本身不受影响**，因为下载页每次打开都现签一个新地址，换完钥匙点开照样能下。

**CORS 配置被改坏**
- 出事情形：改桶设置时把 CORS 删了/改错，或者换了新域名忘了加进来。
- 后果：网页能打开，但浏览器上传会被跨域策略拦下、报错传不上；下载和后台都不受影响。
- 重建步骤：R2 → 桶 →「设置」→ CORS 策略，把仓库里 `r2-cors.json` 的内容整段贴回（`AllowedOrigins` 里要包含你实际在用的全部站点地址：pages.dev 地址 + 自定义域名，一个都别落）→ 保存 → 回站点强刷（Ctrl+F5）再传一次验证。
- 影响范围：只影响改坏这段时间的上传，贴回来即恢复，没有数据损失。

**清理任务（cleanup）停了**
- 出事情形：GitHub 仓库 60 天没动静，Actions 的定时任务被平台自动停用；或 `TASK_SECRET` / `SITE_URL` 配错；调清理的外部调度（如果有）停了又没开工作流自带定时。
- 后果：**没人会报错，站点照常**——但过期文件不再自动删、超时未完成的上传记录一直堆着，R2 用量只涨不降，涨满 10 GB 后新文件就传不上来了。
- 怎么发现：CF 控制台 R2 页看用量只涨不降；或 GitHub 仓库 →「Actions（操作）」→ cleanup 工作流，最近的运行记录是红色、显示已停用、或者好几天没有新记录。
- 怎么办：① Actions → cleanup，若页面提示定时工作流已被停用，点「启用（Enable workflow）」；② 点「Run workflow（运行工作流）」手动跑一轮，看它变绿；③ 顺手核对 GitHub Secrets 里 `TASK_SECRET` 和 Pages 里那份一字不差、`SITE_URL` 还是现在能打开的站点地址。
- 影响范围：停摆期间只是不清东西、不丢数据；恢复后第一轮会把积压的过期文件一并清掉（每轮最多清 200 条，积压太多就连着多跑几轮）。

**Pages 项目被删**
- 出事情形：控制台里把 Pages 项目删了，或项目损坏要重建。
- 后果：站点地址打不开；但文件在 R2、记录在 D1，都完好——丢的只是「门面」和项目里的配置。
- 重建步骤：① 先按方式二（传部署包）或方式一（连 GitHub）把项目重建出来、能打开；② 项目 →「设置」→「绑定」：D1 绑定变量名填 `DB`、选回原来的数据库，R2 绑定变量名填 `FILES`、选回原来的桶（变量名必须一字不差，代码是按名字找的）；③ 「变量和密钥」按凭据一览逐项重填：普通变量 `R2_S3_ENDPOINT`、`R2_S3_BUCKET`，密钥 `R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`、`TASK_SECRET`、`IP_SALT`；④ 「自定义域」把原域名重新绑回来。
- 影响范围：域名绑回去之后，**旧分享链接能接着用**（链接只认域名和记录，两样都没动过）；只有重建这段时间站点打不开。

**`TASK_SECRET` 换了 / 两边不一致**
- 先说清：它只管清理接口 `/api/cleanup` 的口令，**和分享链接、上传、下载一点关系都没有**。
- 后果：Pages 里那份和 GitHub Secrets 里那份对不上时，清理任务每次调用都被拒（401），表现和上面「清理任务停了」一模一样；除此之外全站毫无影响。
- 怎么办：想换就大大方方换——生成一个新值，**Pages 和 GitHub 两边同时改成新值**，再跑一轮清理验一下变绿即可。忘了原值也不要紧，反正两边一起换新的，不需要知道旧的。

**`IP_SALT` 换了**
- 后果：它只参与「把访客 IP 哈希之后再限流计数」这一步。换盐之后，新算的哈希和旧记录对不上，等于**每个人的限流计数清零重来**（之前被限流卡住的人，暂时又能传几次）；对不上的旧记录没人再用，清理任务会在 7 天内顺手删掉。
- 影响范围：仅此而已。文件、记录、链接、其他钥匙全不受影响，换完什么都不用做。

**域名过期**
- 出事情形：绑的自定义域名忘了续费。
- 后果：自定义域名打不开、用这个域名发出去的分享链接也打不开；但 `*.pages.dev` 备用地址还能开，文件和记录都完好。
- 怎么办：还在注册商给的宽限期内 → 立刻续费，解析会自己恢复，什么都不用改；已经过期被别人抢注 → 只能换新域名：Pages →「自定义域」绑上新域名，并同步改两处：R2 桶 CORS 的 `AllowedOrigins` 加上新域名、GitHub Secret `SITE_URL` 换成新地址。
- 影响范围：旧域名发出去的链接作废，要用新链接重新发；站内数据不受影响。

**GitHub 仓库被删**
- 出事情形：仓库被误删或账号出问题。
- 后果：Cloudflare 上的站点**照常跑**（代码早就部署上去了）；丢的是源码和仓库里的自动化——自动部署没了、cleanup 工作流也没了（清理会跟着停，后果见上面那条）。
- 重建步骤：① 新建一个仓库，把最新发行包 zip 解压后上传（本地还留着源码的直接推源码）；② 仓库 →「Settings（设置）」→「Secrets and variables」→「Actions」，按部署章节把 Secrets 重新配齐（`CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`、`TASK_SECRET`、`SITE_URL` 等）；③ 手动各 Run 一次 deploy 和 cleanup 两个工作流，确认都变绿。
- 影响范围：重建期间站点一直可用；只是这段时间别指望自动部署和自动清理。

## 可选：绑你自己的域名

1. Pages 项目 →「自定义域（Custom domains）」→「设置自定义域」→ 填你的域名（如 `file.你的域名.com`）→ 按提示去域名 DNS 处加一条 CNAME 记录（域名本来就在 Cloudflare 托管的话它会自动加）。
2. 等状态变成「活动（Active）」，用新域名打开站点确认正常。
3. **必做补漏**：把新域名加进 R2 桶 CORS 的 `AllowedOrigins`（共同准备第 2 件），否则新域名下上传会 CORS 报错。
4. 用了 cleanup 工作流的，把 GitHub Secret `SITE_URL` 改成新域名地址，清理任务才会调新地址。

## 怎么用（给访客看的）

1. 打开站点，点「选择文件」（一次传 1 个文件，单个不超过 5 GB）；
2. 选有效期（1 / 6 / 12 小时、1 / 3 / 7 天）和下载次数（不限 / 1 次 / 5 次 / 10 次）；
3. 点「开始上传」，传完复制下载链接发给对方；
4. 对方打开链接直接下载，下载文件名就是原文件名（中文名正常）。

几个容易误会的点，写清免得来问：

- **有效期从「上传完成」那一刻开始算**，不是从点上传开始算。文件大、网速慢、传了很久才传完，可下载时间就从传完那刻起算足时长；但反过来，链接要等传完才生成，别在还没传完时就把「正在生成」的页面发给人。
- 链接到期或下载次数用完就失效：到期文件会被删除，次数用完的会在 1 小时内删除（让已经领到直链的人把文件下完），不用手动清理。
- 传到一半关掉页面：这个文件不会生成可用链接，半成品记录会在上传地址失效后（约 6 小时）被定时清理，不占长期空间。

## 探活：怎么知道站点还活着

探活（一句话：定时派个程序去敲一下你的站点，看它还应不应答，应答要多久）能让你在访客投诉之前就知道站点挂了。

本站的探活分工是另一个小工具 **ym-dash**（站长自己的站点测活总览，每 30 分钟自动把名单上的站点挨个探一遍）在做。你想给自己部署的这份也加上探活，照着做：

**需要什么**：一个 ym-dash 实例（你自己的或站长的，总之是一个能定时发请求的总览页）。

**怎么加（在 ym-dash 里操作）**：

1. 打开 ym-dash，登录后台 →「站点管理」→「添加站点」。
2. 名称填你认得出的名字（如「传文件」），URL 填你的站点地址 `https://你的项目名.pages.dev`（或你的自定义域名，根地址即可，不用带路径）。
3. 保存后点一次「立即检测」：返回 **200**、响应几百毫秒内，就是活的。
4. 之后每 30 分钟自动探一次，结果在 ym-dash 总览页看：哪个站绿（正常）、哪个红（异常）、各自响应多少毫秒，一眼可知。

**探什么才算真活**：探首页 200 只能说明静态页还在。真要确认上传下载链路通，得偶尔手动走一遍「部署完怎么验」的第 1、2 项（传个小文件能下回来）。探活是日常哨兵，深度自测靠自测清单，两个别互相替代。

## 保活：平时要盯什么

**结论：核心服务不需要保活动作。** Pages、R2、D1 都没有休眠机制，不用定期登录或发请求「叫醒」它们；`pages.dev` 的证书由 Cloudflare 自动续。平时真正要盯的就四件：

1. **R2 用量别超免费额**：免费额是 10 GB 存储（全站上限也按 10 GB 卡），以及每月一档免费的操作次数。文件都是短期的，一般涨不上去；在 CF 控制台 R2 页能看用量，接近上限时先手动跑一次清理（见下节）或等最早的文件过期。
2. **GitHub 定时任务别被停用**：GitHub 会停用长期没有活动的公开仓库的定时工作流。本项目的 cleanup 就跑在上面——每隔一两个月去仓库「Actions」页看一眼 `cleanup` 最近有没有按时跑；若看到定时工作流被停用的提示，点「重新启用（Enable workflow）」。本站另有一层外部调度器约每 300 分钟补触发一次 cleanup（见下节），GitHub 定时偶尔迟到也不怕；（fork 自建的人没有这层外部调度，靠 GitHub 自带定时即可，迟到几十分钟对 6 小时一轮的清理无实质影响。）
3. **自定义域名到期续费**（绑了域名才相关）：域名过期站点立刻打不开，提前续。
4. **钥匙别手贱删**：R2 的 API 令牌、Pages 里的密钥删掉，上传立刻停摆；删之前先想好替代的配好没。

## 自动更新 / 自动任务

代码更新没有「上游自动合并」这类机制：你改完代码推送一次，部署按你选的方式走（方式一自动，方式二手动传包，方式三一条命令）。自动跑的是下面这三件，都在 GitHub Actions 里，**在哪看**统一是：仓库页 →「Actions」标签 → 点工作流名看每一轮的绿勾/红叉，点进去能看每一步日志。

| 自动任务 | 谁触发 | 频率 | 怎么手动触发 | 失败了怎么办 |
|---|---|---|---|---|
| `deploy` 部署（仅方式一 B 路线） | 推送到 `main` 分支 | 每次推送 | Actions 页 → `deploy` →「Run workflow」 | 看红叉那一步的日志：多半是 Secrets 缺/错（令牌、账号 ID）。没配令牌时它会自己跳过并提示，不算失败——用 A 路线的人看到它跳过是正常的 |
| `cleanup` 定时清理 | GitHub 定时器（仓库自带 schedule，每 6 小时，UTC 整点后 17 分）+ 本站另有外部调度器约每 300 分钟补触发一轮（双保险，防 GitHub 定时迟到） | 约每 6 小时一轮 | Actions 页 → `cleanup` →「Run workflow」；前提是 GitHub Secrets 里配了 `SITE_URL` 和 `TASK_SECRET`，没配它会提示并跳过（不报错） | 先查两个 Secret 在不在、`TASK_SECRET` 和 Pages 里的是不是同一个；接口本身可重复调，不会多删，修好再跑一次即可 |
| `ci` 测试 | 推送 / 提 PR | 每次 | Actions 页 → `ci` →「Run workflow」 | 红了说明这版代码没过自带测试，先别部署，回本地 `npm test` 复现修好再推 |

**过期文件的三层清理**（不全靠 cleanup 一条线）：① cleanup 定时调 `/api/cleanup`（删 R2 对象成功后才删 D1 记录，删失败的留到下轮重试）；② 有人打开过期/用完的链接时顺手删；③ R2 桶生命周期 10 天兜底删。方式二（没接 GitHub）的人有 ②③ 两层，文件不会无限堆积，但建议有条件时把 cleanup 接上。

## 技术原理

Cloudflare Pages + Pages Functions + R2 + D1，零构建步骤，全部跑在免费额度内。

- **上传走 R2 预签名 PUT 直传**：浏览器直接把文件 PUT 到 R2，不经过 Worker/Function（Worker 单请求有大小上限，传大文件必须绕过它；单次 PUT 上限 5 GB）。
- **下载走 R2 预签名 GET 跳转**：`/d/<链接ID>` 查元数据后 302 跳到 R2 的预签名地址，文件字节不经过 Worker。
- **元数据存 D1**：随机链接 ID、原文件名、大小、过期时间、下载次数与上限。下载计数在有上限时用条件更新先原子占位再放行，并发请求不会把次数超发。
- **过期清理三条线**：GitHub Actions 每 6 小时调 `/api/cleanup`（带密钥校验；对象删除成功后才删记录，删失败的下次重试）；访问到过期/用完链接时顺手删；R2 桶生命周期 10 天兜底。
- **容量口径**：未过期的已就绪文件 + 保留期（6 小时 10 分）内新建的待上传占 10 GB 上限，超了返回 413。保留期不短于上传地址有效期（6 小时）+ 10 分钟缓冲，保证慢速大文件传满全程记录都在、传完能确认。
- **限流**：同一 IP 每小时最多创建 10 次上传（IP 只存哈希），超了返回 429。

## 别人部署和本站不一样的地方（Fork 差异）

1. **存储与数据库是空的**：R2 桶与 D1 库要自己建；本站已有的文件、链接不会过去（数据在部署者的 R2/D1 里，不在代码里）。按上文建同名桶和库、执行 `schema/0001_init.sql`、`schema/0002_add_max_downloads.sql`（和可选的 0003），功能就一样，但历史文件仍然没有——文件本体从不进仓库。
2. **密钥必须自己生成**：R2 的 S3 凭据（`R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`）与清理口令（`TASK_SECRET`）不在仓库里；部署时自己在 Cloudflare 生成/自己编，分别填进 Pages 后台与 GitHub Secrets。没有密钥就签发不了上传地址——这是故意的，密钥不能共享。
3. **绑定与变量在后台配，仓库里没有真实资源标识**：`database_id`、R2 端点（账号 ID）这些值不进仓库，只有 `wrangler.toml.example` 示例。部署时在 Pages 后台绑定你自己的库和桶、填你自己的端点，不存在「照原样部署绑到别人资源」的问题。
4. **定时清理要自己配**：`.github/workflows/cleanup.yml` 每 6 小时调一次清理接口，需要配 `SITE_URL` 与 `TASK_SECRET` 两个 GitHub Secrets；不配的话过期文件只靠「访问过期链接时顺手删」和桶生命周期兜底，不会定时删。若你的 GitHub 定时任务经常迟到，也可以另加一层外部调度补发（可选）。
5. **10 GB 上限人人一样**：这是 Cloudflare 免费 R2 的上限，不是本站特有的。想存更多只能付费升级 R2，然后改代码里的容量常量（`functions/api/upload-init.js`、`functions/api/stats.js`、`public/index.html` 三处一起改）；单文件仍受 5 GB 单次 PUT 上限约束，超过要改成分片上传，目前代码不支持。
6. **域名不同**：默认是 `xxx.pages.dev` 这样的默认子域，自己的域名要在 Pages 里另行绑定。
7. **代码功能完全一样**：上传、下载、过期、限流、统计、中文界面都在代码里，部署后直接就有，不用再配。

## 和同类有什么不同 · 优点 · 缺点

**和同类有什么不同**

- 商业传文件服务（奶牛快传、文叔叔等）文件在别人服务器上、免费档各种限速限量；这个部署在自己账号里，规则自己定，数据不出自己的地盘。
- 比自建 FTP/网盘轻得多：没有服务器要维护，Cloudflare 免费额度内零成本运行。

**优点**

- 免注册、打开就传：生成一个分享链接发给对方就能下载，适合临时传文件。
- 分享可控：能设下载次数和有效期，过期自动失效，不用事后惦记着删。
- 自托管：文件存在你自己的 Cloudflare 账号里，不经过任何第三方网盘，不用看会员和限速的脸色。
- 上传下载都走存储直连，不占服务器带宽，速度取决于 Cloudflare 节点。
- 两种部署方法都只是换程序：已上传的文件在你自己账号的存储桶里、分享记录在数据库里，重新部署不会丢。

**缺点 / 要花钱的地方**

- 本身 0 元，跑在 Cloudflare 免费额度上；花钱的只有自备域名（可选）。
- 免费存储有上限（10 GB 级别），定位是临时中转，不是长期网盘，别拿它存家当。

## 常见问题

**部署类**

- **传到一半失败 / 上传报 CORS 错**：十有八九是 R2 桶的 CORS 没配好。依次查：桶的「设置 → CORS 策略」配了没有；`AllowedOrigins` 里有没有你**当前正在用的**站点地址（pages.dev 默认地址和自定义域名要分别加）；`AllowedMethods` 里有没有 `PUT`；`AllowedHeaders` 里有没有 `Content-Type`。改完 CORS 不用重新部署，刷新页面重传即可。
- **`/api/upload-init` 返回 500 `sign_failed`**：R2 的 S3 钥匙没配或配错。查 Pages「变量和密钥」里 `R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY` 在不在、值对不对，再查普通变量 `R2_S3_ENDPOINT` 里账号 ID 写对没。改完要重新部署一次才生效。
- **`upload-complete` 返回 `not_uploaded`**：浏览器那下 PUT 没成功（按 F12 看浏览器控制台的网络请求），常见是 CORS 没过，或预签名地址已过期（上传地址有效 6 小时，超大文件别拖太久才点确认）。
- **下载链接 404**：文件可能已过期被清理，或上传没走完确认（记录状态还是 pending）。先传个小文件走一遍自测清单定位。
- **改了绑定/变量/密钥却不生效**：Pages 的这些配置都是「下一次部署生效」，去部署页对最新部署点「重新部署」。
- **部署后接口全 404、只有静态页**：部署的目录结构错了——要么方式三没拼 `_site`，要么方式二上传多套了一层文件夹。回对应方式的步骤核对目录结构。

**使用类**

- **为什么提示空间不足（413）？** 全站 10 GB 是所有使用者共用的（你自己部署就是你一个人用），等最早的文件过期释放，或手动跑一次 cleanup 工作流。
- **链接发错人了怎么办？** 链接没法单独撤销，可以等它到期自动失效。有效期选得越短，风险窗口越小，敏感文件建议选 1 小时 + 下载 1 次。
- **对方下载慢？** 下载是对方浏览器直接从 R2 拉文件，不经过本站服务器，速度取决于对方网络与 R2 节点。
- **能传 5 GB 以上吗？** 不能。单次 PUT 的上限就是 5 GB，要传更大的请先分卷压缩。

## 已知问题 / 已知边界

- **上传地址在过期前可重复 PUT**：预签名 PUT 地址有效 6 小时，确认上传后到地址过期前，持有该地址的人可以覆盖同一文件对象（预签名地址本身无法撤销）。因为本站是无注册的临时分享、链接 ID 本身就是凭证，风险窗口等同于分享链接泄露；若要彻底关掉，需要确认上传后把对象复制到新键并删旧对象——那会产生一笔与文件等大的额外流量与复杂度，本版未采用，记录在此供取舍。
- **下载次数计的是「领取」**：经下载页领到直链后，直链在有效期内（最长 1 小时）可反复下载，这是预签名直链的固有形态，无法按真实下载次数计量。
- 单个文件的大小受 Cloudflare 免费通道的请求大小限制，超大文件请分卷或换其他方式传。
- 分享链接的有效期从上传完成时开始算，文件传得慢时实际可下载时间会相应缩短，急用先确认上传完成再发链接。
- 免费额度的请求次数是账号级的：同账号还有其他项目时，传文件的高频下载会和它们共用每日请求量。

## 总共要花多少钱

先说大实话：**照本文的用法，0 元。** 逐项算给你看：

| 项目 | 免费额度 | 本项目的实际用量 |
| --- | --- | --- |
| Pages（网站托管 + 接口） | 每月 500 次部署、请求次数免费档管够 | 零头，碰不到顶 |
| D1（分享记录） | 每天 500 万行读、10 万行写、总共 5 GB | 一条记录就几百字节，离顶十万八千里 |
| R2（存文件） | 每月 10 GB 存储 + 一档免费的操作次数 | 这是唯一要盯的：代码已把全站容量卡在 10 GB 上限，满了会提示等旧文件过期 |
| GitHub | 免费账号的 Actions 分钟数管够（公开仓库基本不限量口径） | 部署 + 每 6 小时一轮清理，花不了多少 |

两个花钱的口子提前说清，免得日后意外：

1. **R2 开通时要绑一张银行卡**（Cloudflare 的规矩，验证用）。免费额度内不扣钱；真超过免费额了才按量扣，大致口径是存储约 $0.015 / GB / 月、操作次数按每百万次计价——以 CF 控制台当时的官方价为准。本项目文件都是短期过期的，正常个人使用基本贴着免费额走不到收费区。
2. **只有你主动把容量上限改大、长期存超过 10 GB 的文件**，才会稳定进入 R2 付费区。改不改在你，代码里的上限就是你的保险丝。

## 安全提醒

1. **分享链接本身就是钥匙**：本站不设账号、不设密码，有效期和次数之内，谁拿到链接谁就能下载。所以链接别往公开的群、论坛、评论区贴；传敏感文件时选**最短有效期 + 下载 1 次**，对方下完链接自己就废了。
2. **部署用的钥匙只进两个地方**：密码管理器、后台的密钥区。永远不要写进仓库文件、不要截图发群里问人——代码仓库是公开的，写进去等于当场公开。
3. **GitHub 和 Cloudflare 两个账号都打开两步验证（2FA）**：CF 账号被盗 = 站点和文件一起丢；GitHub 账号被盗 = 代码和自动部署被接管。开 2FA 的入口都在各自的账号设置 → 安全里。
4. **怀疑钥匙泄露，先删后建**：去 R2 的「API 令牌」把旧令牌删掉——删掉的那一刻，对方手里的钥匙立刻作废；然后再按「出事了怎么办」里那条建新的换上。顺序反了（先建新、旧的不删）等于没止损。
5. **站长侧没有「找回密码」这回事**：本项目没有给访客的账号体系，你要守的就是上面两个平台账号 + 那几把钥匙，按凭据一览存好就行。
